# twich-analog — видеоплеер через MediaMTX

Учебный аналог Twitch: OBS отправляет поток на медиасервер **MediaMTX**, а браузер смотрит его через **WebRTC (WHEP)** или **HLS**. Фронтенд — React + Vite, бэкенд авторизации — FastAPI (пока к видео не подключён).

```
 ┌──────────┐   RTMP :1935    ┌───────────┐   HLS :8888    ┌──────────┐
 │   OBS    │ ──────────────► │ MediaMTX  │ ─────────────► │  Браузер │
 │ (камера) │                 │ (сервер)  │   WHEP :8889   │  (React) │
 └──────────┘                 └─────┬─────┘ ─────────────► └──────────┘
                                    │ REST API :9997
                                    └────────► список эфиров, зрители, кодеки
```

---

## 1. Зачем вообще нужен MediaMTX

Браузер не умеет напрямую принимать RTMP из OBS. OBS тоже не умеет отдавать WebRTC-зрителям сотни подключений. Между ними нужен посредник — медиасервер, который:

1. **принимает** поток по «тяжёлому» протоколу публикации (RTMP/RTSP/SRT),
2. **переупаковывает** его на лету в то, что понимает браузер (HLS/WebRTC),
3. **размножает** один входящий поток на много зрителей (не грузя канал стримера),
4. **отдаёт метаданные** через API (кто в эфире, сколько зрителей, какие кодеки).

MediaMTX — это такой сервер в одном бинарнике: без зависимостей, без Docker, без БД. Именно поэтому он удобен для учебного проекта: `mediamtx.exe mediamtx.yml` — и всё работает.

**Что было бы без него:** пришлось бы писать свой сервер на Node/Python с перекодированием через ffmpeg, раздачей HLS-сегментов, ICE/STUN для WebRTC и учётом зрителей. MediaMTX делает это из коробки.

## 2. Что где лежит

| Путь | Роль |
| --- | --- |
| `mediamtx.yml` | конфиг медиасервера: порты, CORS, пути, запись |
| `start-mediamtx.ps1` | запуск MediaMTX с этим конфигом |
| `tools/mediamtx/mediamtx.exe` | сам сервер (v1.21.4, скачан с GitHub) |
| `frontend/` | React-приложение: плеер, список эфиров, подсказки для OBS |
| `frontend/src/components/VideoPlayer.jsx` | вся логика HLS + WebRTC-плеера |
| `frontend/src/lib/mediamtx.js` | адреса и хелперы MediaMTX: URL потоков, настройки OBS |
| `frontend/src/hooks/useStreams.js` | опрос `/v3/paths/list` раз в 3 секунды |
| `backend/main.py` | FastAPI-авторизация (к видео пока не относится) |

## 3. Как запустить

Нужны два процесса (в двух окнах терминала).

**Окно 1 — медиасервер:**

```powershell
.\start-mediamtx.ps1
```

Должно появиться:

```
INF MediaMTX v1.21.4, windows, amd64
INF [RTMP] started with listener on :1935 (TCP/RTMP)
INF [HLS] started with listener on :8888 (TCP/HTTP)
INF [WebRTC] started with listeners on :8889 (TCP/HTTP), :8189 (UDP/ICE)
INF [API] started with listener on 127.0.0.1:9997 (TCP/HTTP)
```

**Окно 2 — фронтенд:**

```powershell
cd frontend
npm install        # один раз
npm run dev
```

Откройте http://localhost:5173 — плеер покажет «Поток офлайн», это нормально: эфира ещё нет.

**Окно 3 — OBS** (если OBS нет или не ставится — см. раздел 4, там вариант вообще без установки):

1. Настройки → Вещание → Сервис: **Настраиваемый**.
2. Сервер: `rtmp://127.0.0.1:1935/live`
3. Ключ потока: `stream`
4. «Начать трансляцию».

Через 1–2 секунды в MediaMTX появится путь `live/stream`, плеер сам переподключится и покажет картинку (переподключение раз в 3 секунды, кнопка «Повторить сейчас» тоже есть).

> Имя пути складывается из URL: `rtmp://host/<сервер>/<ключ>` → `live/stream`. Это аналог «канала» на Twitch: путь можно назвать как угодно (`live/вася`, `games/minecraft`), и открыть его в плеере по имени.

## 4. Если OBS поставить нельзя (нет прав администратора)

Есть три варианта — от «ничего не скачивать» до портативного OBS.

### 4.1. Прямо из браузера — ничего не устанавливать

MediaMTX умеет принимать WebRTC-поток с камеры браузера и сам отдаёт страницу публикации:

```
http://localhost:8889/live/stream/publish
```

Откройте её в Chrome/Edge на том же компьютере, где запущен MediaMTX:

1. разрешите камеру и микрофон;
2. выберите устройства;
3. выберите видео-кодек **H264** и аудио **Opus**;
4. нажмите **Publish**.

Через секунду путь `live/stream` появится в плеере. H264 выбран не случайно: HLS в MediaMTX поддерживает H264/VP9/AV1/H265, а VP8 (его браузер предлагает по умолчанию) — нет. С VP8 будет работать только WebRTC-просмотр, HLS — нет.

Ссылка «Открыть страницу публикации» есть прямо в панели «Выйти в эфир» под плеером.

Ограничения: это камера, а не экран; страница должна открываться по `localhost` (браузеры дают доступ к камере только на «безопасных» адресах, `http://192.168.x.x` уже не подходит); браузерный энкодер слабее OBS.

### 4.2. OBS portable (ZIP) — без установки и без админа

Официальный OBS выкладывают ещё и ZIP-архивом, который не требует установки:

1. https://github.com/obsproject/obs-studio/releases/latest
2. скачайте `OBS-Studio-...-Windows-x64.zip`;
3. распакуйте, например, в `C:\Users\<вы>\obs`;
4. запустите `bin\64bit\obs64.exe`.

Настройки те же: сервер `rtmp://127.0.0.1:1935/live`, ключ `stream`. Windows может спросить про доступ к сети — разрешите для частных сетей.

### 4.3. ffmpeg portable — для экрана и камеры

ffmpeg не требует установки: распакуйте `ffmpeg.exe` и запустите команду. Захват экрана со звуком:

```powershell
ffmpeg -f gdigrab -framerate 30 -i desktop -f dshow -i audio="Микрофон" `
  -c:v libx264 -preset veryfast -tune zerolatency -pix_fmt yuv420p -g 60 `
  -b:v 2500k -c:a aac -b:a 128k -f flv rtmp://127.0.0.1:1935/live/stream
```

Захват камеры (имя устройства покажет `ffmpeg -list_devices true -f dshow -i dummy`):

```powershell
ffmpeg -f dshow -i video="USB Video Device" -f dshow -i audio="Микрофон" `
  -c:v libx264 -preset veryfast -tune zerolatency -pix_fmt yuv420p -g 60 `
  -b:v 2500k -c:a aac -b:a 128k -f flv rtmp://127.0.0.1:1935/live/stream
```

Сборка без установки: https://www.gyan.dev/ffmpeg/builds/ (essentials). Именно ей я проверял плеер на синтетическом потоке.

## 5. Как это работает по шагам

### Шаг 1. Публикация (OBS → MediaMTX, RTMP, порт 1935)

OBS кодирует картинку в H.264 и звук в AAC и отправляет их по RTMP. MediaMTX принимает соединение, читает имя пути из URL и создаёт у себя объект «путь» (path) — это и есть канал.

Важно: MediaMTX **не перекодирует** видео (по умолчанию). Он передаёт те же H.264/AAC дальше. Поэтому серверу почти не нужен CPU — только сеть.

### Шаг 2. Просмотр через HLS (порт 8888)

MediaMTX нарезает поток на короткие фрагменты и отдаёт их по обычному HTTP:

- плейлист `http://127.0.0.1:8888/live/stream/index.m3u8`
- фрагменты `.m4s`/`.ts` рядом.

Браузер скачивает плейлист и играет сегменты. Это работает везде (в том числе в Safari/iOS без библиотек), но по своей природе отстаёт: сегмент должен «дозреть», плюс буфер плеера. В конфиге включён `hlsVariant: lowLatency` (LL-HLS) с сегментами 1 c и part 200 мс — это даёт задержку примерно 2–5 c вместо классических 15–30 c.

В коде это делает **hls.js**:

```js
hls = new Hls({ lowLatencyMode: true })
hls.loadSource(hlsUrl(path))   // .../live/stream/index.m3u8
hls.attachMedia(video)
```

`hls.js` нужен потому, что Chrome/Firefox не умеют HLS нативно (в отличие от Safari) — библиотека скачивает плейлист, склеивает фрагменты и кормит их в `<video>` через Media Source Extensions.

В коде hls.js подключается первым, а нативный HLS остаётся запасным вариантом для Safari/iOS: некоторые браузеры (Electron, встроенные webview) формально заявляют поддержку HLS, но не понимают low-latency-плейлисты MediaMTX и падают с `DEMUXER_ERROR_COULD_NOT_PARSE`.

### Шаг 3. Просмотр через WebRTC / WHEP (порт 8889)

WebRTC — тот же стек, что у видеозвонков: минимальная задержка (~0.3–1 c), но нужен обмен SDP/ICE. Для «смотрения» существует профиль **WHEP** (WebRTC-HTTP Egress Protocol): offer/answer передаются обычными HTTP-запросами, ICE-сервер не обязателен.

Рукопожатие в `VideoPlayer.jsx`:

```js
const pc = new RTCPeerConnection({ iceServers: [] })
pc.addTransceiver('video', { direction: 'recvonly' })
pc.addTransceiver('audio', { direction: 'recvonly' })

const offer = await pc.createOffer()
await pc.setLocalDescription(offer)

// POST SDP на MediaMTX
const res = await fetch('http://127.0.0.1:8889/live/stream/whep', {
  method: 'POST',
  headers: { 'Content-Type': 'application/sdp' },
  body: offer.sdp,
})

await pc.setRemoteDescription({ type: 'answer', sdp: await res.text() })
// ответ приходит по RTCPeerConnection, видео — в pc.ontrack
```

При закрытии вкладки/смене канала плеер делает `DELETE` на URL сессии из заголовка `Location` — иначе MediaMTX будет считать зрителя активным.

Медиа идёт не по HTTP, а по **UDP** (порт 8189), поэтому на этом же ПК всё работает сразу, а для просмотра с другого устройства в `mediamtx.yml` нужно указать IP сервера в `webrtcAdditionalHosts` и открыть порты в брандмауэре.

### Шаг 4. Список эфиров (REST API, порт 9997)

`GET http://127.0.0.1:9997/v3/paths/list` отдаёт JSON:

```json
{
  "items": [
    {
      "name": "live/stream",
      "ready": true,
      "readyTime": "2026-11-18T12:00:00Z",
      "tracks": ["H264", "AAC"],
      "readers": [{ "type": "webRTCSession", ... }],
      "bytesReceived": 12345678
    }
  ]
}
```

`useStreams.js` опрашивает этот эндпоинт раз в 3 секунды. Отсюда в интерфейсе: статус «в эфире», число зрителей, время эфира, кодеки, объём принятых данных. CORS для этих запросов разрешён в конфиге (`apiAllowOrigins`).

## 6. HLS или WebRTC — что выбрать

| | HLS | WebRTC (WHEP) |
| --- | --- | --- |
| Задержка | 2–8 c | 0.3–1 c |
| Совместимость | любая (нужен только HTTP) | Chrome, Firefox, Safari, Edge |
| Нагрузка | лёгкая, кэшируется CDN | чуть выше, UDP-сессии |
| Когда использовать | «как YouTube», много зрителей, мобильные | стрим с чатом, интерактив, игры |

В интерфейсе есть переключатель — можно сравнивать задержку на одном и том же эфире.

---

## 7. Что уже умеет плеер

- автопереподключение к потоку каждые 3 секунды (поток может начаться позже);
- переключение WebRTC ↔ HLS без перезагрузки страницы;
- корректная очистка ресурсов: `hls.destroy()`, `pc.close()`, `DELETE` WHEP-сессии;
- автоплей без звука (политика браузеров) + кнопка «Включить звук»;
- живые метрики из API: зрители, кодеки, время эфира, принято байт;
- список активных каналов и переход на любой путь;
- готовые поля «сервер/ключ» для OBS с копированием в один клик;
- кнопка «Открыть страницу публикации» — можно выйти в эфир прямо из браузера, без OBS и без прав администратора.

## 9. Настройка под себя

Все адреса фронтенда — в `frontend/.env` (образец рядом: `.env.example`). Если меняете порт, поменяйте его и в `mediamtx.yml`, и в `.env`.

Просмотр с телефона в той же Wi-Fi:

1. в `mediamtx.yml` → `webrtcAdditionalHosts: ["192.168.x.x"]` (IP ПК);
2. в `frontend/.env` → `VITE_MEDIAMTX_HOST=192.168.x.x`;
3. перезапустить MediaMTX и `npm run dev`;
4. в брандмауэре Windows разрешить `mediamtx.exe` (порты 1935, 8888, 8889/8189, 9997).

Запись эфиров (VOD): раскомментируйте блок `record` в `mediamtx.yml` — файлы появятся в `recordings/<путь>/`. Отдавать их браузеру можно через FastAPI (позже — «прошлые трансляции» на Twitch-аналоге).

Пароль на публикацию: в `mediamtx.yml` для пути добавить `publishUser`/`publishPass` (или `publishUser` = `any`), либо включить глобальную аутентификацию (`authMethod: internal`). Сейчас публикация открыта — это удобно для локальной учёбы, но не для интернета.

## 10. Частые проблемы

| Симптом | Причина / решение |
| --- | --- |
| Плеер «Поток офлайн», в MediaMTX пусто | OBS не нажал «Начать трансляцию», неверный сервер/ключ, другой порт |
| «MediaMTX не запущен» в шапке | не запущен `start-mediamtx.ps1` либо порт 9997 занят |
| HLS играет, WebRTC нет | UDP 8189 закрыт; для другого ПК не указан `webrtcAdditionalHosts`; встроенный/корпоративный браузер не даёт ICE-кандидатов — откройте в обычном Chrome/Edge или переключитесь на HLS |
| Картинка есть, звука нет | OBS не захватывает аудио или браузер заглушил автоплей — нажмите «Включить звук» |
| Ошибка CORS в консоли | фронтенд открыт не на `http://localhost:5173` — добавьте origin в `apiAllowOrigins`/`hlsAllowOrigins` |
| Задержка HLS 10+ c | это норма для HLS; переключитесь на WebRTC |
| PowerShell не даёт запустить `start-mediamtx.ps1` | `powershell -ExecutionPolicy Bypass -File .\start-mediamtx.ps1` |

## 11. Почему не «просто video src»

`<video src="...">` умеет только обычные файлы (MP4) и HLS в Safari. Живой поток — это бесконечный файл, которого ещё нет целиком, плюс нужны задержка, переподключение, выбор протокола. Поэтому в проекте два уровня:

- **транспорт** — MediaMTX (превращает RTMP в HLS/WebRTC);
- **клиент** — hls.js / RTCPeerConnection + React-состояние (статусы, ретраи, интерфейс).

Дальше логично добавить: JWT-защиту путей (связать с `backend/main.py`), чат, запись/VOD, thumbnail-кадры, категории каналов.
